## 1. 目标与边界

### 1.1 目标
1. **渐进式构建**客户画像（行业焦点、技术倾向、订单模式、交互风格等），用于个性化对话引导；
2. **开放可扩展**：新增画像维度**不改表结构、不重启服务**，只改 Schema 数据；
3. 画像数据**可被 LLM 理解、可校验、可追溯**。

### 1.2 边界（刻意取舍）
- 画像**只影响对话引导**（注入 System Prompt 的 `{user_profile_context}`），**不参与双通道匹配打分**——匹配只看当前需求快照，保持匹配纯净；
- 画像语义为"当前画像"：单用户单行，滚动更新；
- 默认不保留全量历史（`profile_history` 为演进项）；不用于广告/无关推荐。

---

## 2. 设计原则

| # | 原则 | 说明 |
| --- | --- | --- |
| 1 | **Schema 驱动** | 所有维度由 `profile_schemas` 注册表定义（key/type/enum/merge/use_in_prompt），任何读写都过同一 Schema 校验器 |
| 2 | **版本化** | 画像结构带 `schema_version`；加维度 = 升版本，**不碰 DDL** |
| 3 | **增量合并** | LLM 只产出"本次学到什么"的增量建议（updates），由代码按 merge 策略合并，避免整表覆盖丢失历史 |
| 4 | **约束在代码** | LLM 输出仅作建议，代码层做 key/type/枚举/置信度校验，幻觉不直接入库 |
| 5 | **数据隔离** | 客户画像彼此隔离，厂商数据不得混入客户画像 |

## 3. 数据模型

### 3.1 `profile_schemas`（Schema 定义表，可扩展点）
```sql
CREATE TABLE profile_schemas (
  schema_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  schema_version INT NOT NULL,             -- 画像结构版本
  name           VARCHAR(100) NOT NULL,    -- 如 customer_profile_v1
  scope          VARCHAR(20) DEFAULT 'base' CHECK (scope IN ('base','industry')),
  industry       VARCHAR(50),              -- scope=industry 时适用行业（可空=全部）
  dimensions     JSONB NOT NULL,           -- 维度定义数组（见 3.4）
  active         BOOLEAN DEFAULT TRUE,     -- 当前生效版本
  created_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (schema_version, scope, industry)
);
```
> **加维度 = 插入一行新 schema（升级 version）或向 dimensions 追加元素，零 DDL**。这是"开放可扩展"的落点。

### 3.2 `user_profiles`（画像内容）
```sql
CREATE TABLE user_profiles (
  user_id         UUID PRIMARY KEY REFERENCES users(user_id),
  schema_version  INT NOT NULL DEFAULT 1,    -- 指向 profile_schemas
  profile_data    JSONB NOT NULL DEFAULT '{}', -- 画像内容（按 schema 组织）
  confidence      JSONB NOT NULL DEFAULT '{}', -- 每个维度的置信度，如 {"preferred_os": 0.9}
  total_requests  INT DEFAULT 0,
  last_request_at TIMESTAMP,
  created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```
`profile_data` 示例：
```json
{
  "industry_focus": ["机顶盒", "智能音箱"],
  "preferred_os": ["Linux"],
  "common_certifications": ["CE", "FCC"],
  "typical_interfaces": ["网口", "HDMI"],
  "order_pattern": {"moq_typical": 1000, "frequency": "monthly"},
  "interaction_style": "detail_oriented"
}
```

### 3.3 `profile_history`（演进项）
```sql
CREATE TABLE profile_history (
  history_id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       UUID REFERENCES users(user_id),
  before_snapshot JSONB,       -- 更新前画像
  update_signal JSONB,         -- 本次增量建议（可追溯"为什么变"）
  schema_version INT,
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```
> PoC 可不建；用于画像演化回溯与调优。

### 3.4 维度定义（Dimension）契约
`dimensions` 数组元素（LLM 提取时唯一可信的"画像坐标系"）：
```json
{
  "key": "preferred_os",
  "name": "偏好操作系统",
  "type": "string[]",
  "enum": ["Linux", "Android", "RTOS", "其他"],
  "source": "implicit",
  "merge": "append",
  "use_in_prompt": true,
  "queryable": false,
  "description": "用户历史需求中常选的 OS",
  "examples": ["Linux"]
}
```
| 字段 | 作用 |
| --- | --- |
| `key` / `type` | 唯一键与类型（string/number/string[]/object），写入前校验 |
| `enum` | 取值约束（可选），超出则拒绝或归一化 |
| `source` | explicit（用户显式填）/ implicit（LLM 隐式提取） |
| `merge` | **latest**=覆盖 / **append**=去重追加 / **accumulate**=加权累计，合并器据此执行 |
| `use_in_prompt` | 是否注入对话引导（非引导维度不进 Prompt，控制暴露面） |
| `queryable` | 未来是否需要 SQL 过滤/索引（PoC 全 false） |

## 4. 画像提取机制

### 4.1 触发时机
需求确认并生成快照（`customer_requests`）后，**异步**调用（对应架构 3.4 异步层、核心系统需求 3.4 画像异步更新），不阻塞主流程。

### 4.2 提取 Prompt（双 Schema 交 LLM）
```markdown
你是一个用户画像分析专家。基于以下信息，更新用户的画像。

# 画像Schema（严格遵循 key/type/enum，不得自创维度）
{profile_schema}

# 当前画像（最新值，可能为空）
{current_profile_data}

# 本次需求确认记录
{demand_structured}

# 本次会话关键行为摘要
{conversation_signal}

请只输出如下 JSON：
{
  "updates": [
    {
      "key": "preferred_os",        // 必须存在于 Schema
      "value": ["Linux"],           // 符合该 key 的 type/enum
      "confidence": 0.9,            // 0~1，依据是否显式/多次出现
      "merge": "append"             // 建议的合并方式（可选，默认按 Schema）
    }
  ],
  "no_change": true                 // 若无有效信息可更新则为 true，updates 为空
}
```

### 4.3 为什么是"增量建议"而非"整画像重写"
- **防覆盖丢失历史**：每次只写"本次学到什么"，旧维度不被整表冲掉；
- **防幻觉入库**：LLM 输出仅作建议，代码层逐条校验后合并，非法条目丢弃并记日志；
- **可追溯**：每个更新携带来源信号（需求快照/对话摘要）。

### 4.4 合并器（代码层伪代码）
```python
for u in llm_updates:
    if u.key not in schema.dimensions:           continue    # 自创维度丢弃
    if not validate_type(u.value, schema[u.key]): continue  # 类型/枚举校验
    if u.confidence < CONF_THRESHOLD:            continue    # 低置信度丢弃
    merge_fn = schema[u.key].merge
    profile_data[u.key] = merge_fn(profile_data.get(u.key), u.value)
confidence[u.key] = max(confidence.get(u.key, 0), u.confidence)
```
校验规则：key 必须存在于 active schema；type/enum 合法；confidence ≥ 阈值（建议 0.6）；`no_change=true` 时不写。

## 5. 版本化与迁移

| 场景 | 策略 |
| --- | --- |
| **新增维度** | `profile_schemas` 升 version 并置 active；旧用户仍为旧 version |
| **读取兼容（懒迁移）** | 取"用户 schema_version 与 active schema 的并集"——旧用户缺的新维度视为未提取（null），**下次提取时按新 schema 自然补上**，零批量 DDL |
| **删除维度** | 标记 deprecated：不注入、不再提取、保留历史值（不物理删除） |
| **全量重洗** | 可选后台任务：按 active schema 重放/清洗所有画像（演进项） |

## 6. 读取与使用

### 6.1 注入对话引导
新对话开始时：读取 `profile_data` → 按 active schema 过滤 `use_in_prompt=true` 的维度 → 序列化为摘要 → 注入 System Prompt 的 `{user_profile_context}` → Agent 据此不重复询问已知信息、个性化选项。

### 6.2 写入校验
任何入口（提取合并 / 人工修正）都过同一套 Schema 校验器，保证结构一致。

### 6.3 与匹配的关系
画像**不参与**双通道打分；若未来做"个性化排序/重排"，需另行设计且明确权衡（当前刻意排除，保持匹配纯净）。

## 7. 与需求 Schema 的一致性

| | 需求侧（已有） | 画像侧（本设计） |
| --- | --- | --- |
| 结构 | Schema 分层 + 三态 | Schema 维度注册 + merge 策略 |
| 版本 | `customer_requests.version` 快照 | `profile_schemas.schema_version` + `profile_history` |
| 驱动 | LLM 按 Schema 问槽位 | LLM 按 Schema 提取维度 |
| 约束 | 未指定=通配，禁止自由创造 | 自创维度丢弃，类型/枚举校验 |

两端共用同一套"Schema 解析 + 校验 + 版本 + 快照"的心智，代码可复用，产品叙事（可计算、可扩展）统一。

## 8. PoC 落地范围与演进项

**PoC 落地**：
- `profile_schemas` 表 ＋ `user_profiles` 改造（`profile_data` / `confidence` / `schema_version`）；
- 提取 Prompt + 合并器 + 校验器（核心工作量）；
- schema v1 定义 6~8 个核心维度（行业焦点/OS/认证/接口/订单模式/交互风格）。

**演进项**（写入路线，PoC 不做）：
- `profile_history` 快照与画像演化分析；
- `scope=industry` 行业扩展维度（对称于需求侧"品类扩展"）；
- 按 active schema 的全量重洗/清洗任务；
- `queryable=true` 维度的 SQL 索引化；
- 画像时效衰减（老行为权重下降）。
