### 0.1 领域枚举
```python
class IntentType(str, Enum):
    OPTION_CLICK = "option_click"   # 选项按钮点击（确定性写槽位）
    FREE_TEXT    = "free_text"      # 自由文本（LLM 解析，含补充/纠正/排除，即“需求打磨”）
    CONFIRM      = "confirm"        # 确认需求档案
    DONE         = "done"           # 用户主动完成信号（触发确认并提交匹配）
    HELP         = "help"           # 帮助
    DOMAIN_QA    = "domain_qa"      # 领域答疑（A档：与需求决策相关，第 10 章）
    REDIRECT     = "redirect"       # 厂商相关开放问题（B档：重定向匹配详情，第 10 章）
    OFF_TOPIC    = "off_topic"      # 无关话题（C档：守门拉回主线，第 10 章）

class SlotTriState(str, Enum):
    SET      = "set"       # 已指定
    WILDCARD = "wildcard"  # 未指定（通配，null）
    EXCLUDED = "excluded"  # 明确排除（负向过滤）

class CompletionSignal(str, Enum):
    NONE           = "none"             # 未到完成
    AGENT_PROMPTED = "agent_prompted"   # Agent 已主动提示"确认完成？"
    USER_ACTIVE    = "user_active"      # 用户主动完成/确认

class Verdict(str, Enum):               # 与匹配通道B共用
    MATCHED   = "matched"
    PARTIAL   = "partial"
    MISSING   = "missing"
    UNMATCHED = "unmatched"
```

### 0.2 核心状态与消息类型
```python
class SlotValue(TypedDict):
    value: object            # 已指定时的值（str/list/number）
    state: SlotTriState      # 三态

class TurnMessage(TypedDict):
    role: str                # "user" | "assistant"
    content: str
    options: list[str]       # assistant 可选：选项按钮
    slot_delta: dict         # assistant 可选：本轮槽位变化（供前端三态渲染）

class KnowledgeHit(TypedDict):
    knowledge_id: str
    category: str            # terminology/trap/dependency/faq
    content: str
    score: float

class ProfileContext(TypedDict):
    user_id: str
    summary: dict            # {维度key: 值}，已按 use_in_prompt 过滤
    confidence: dict         # {维度key: 置信度}

class AgentState(TypedDict):
    conversation_id: str
    current_slots: dict[str, SlotValue]
    history: list[TurnMessage]
    retrieved_knowledge: list[KnowledgeHit]
    profile_context: ProfileContext | None
    pending_question: str | None       # 当前待追问维度（Schema 未填项）
    completion_signal: CompletionSignal
    archive: dict | None               # 确认后的需求档案
    raw_llm: dict | None               # 上一轮 LLM 原始输出（审计）
    error: str | None                  # 最近一次异常标记
```

### 0.3 组件接口（conversation 域内部）
```python
class StateStore(Protocol):
    """持久化 AgentState 到 PG + 写事实数据"""
    async def load(self, conversation_id: str) -> AgentState
    async def save(self, state: AgentState) -> None
    async def append_event(self, conversation_id: str, seq: int,
                           event_type: str, payload: dict) -> None
    async def log_llm_call(self, call: dict) -> None   # -> llm_call_logs

class Retriever(Protocol):
    """领域知识检索（RAG）"""
    async def retrieve(self, query: str, industry: str | None,
                       top_k: int, min_score: float) -> list[KnowledgeHit]

class ContextBuilder(Protocol):
    """组装每轮 messages（第 3 章）"""
    async def build(self, state: AgentState) -> list[dict]

class OutputValidator(Protocol):
    """校验并结构化 LLM 输出（第 6 章）"""
    async def validate(self, raw: str, schema: type) -> dict

class AgentOrchestrator(Protocol):
    """Agent 主入口：接收消息 → 返回回复"""
    async def handle_message(self, conversation_id: str,
                             message: str | None,
                             clicked_option: str | None) -> AgentReply

class AgentReply(TypedDict):
    text: str
    options: list[str]
    updated_slots: dict[str, SlotValue]
    completion_flagged: bool
    archive: dict | None     # confirm/done 后返回
    error: str | None
```

## 1. 目标与设计原则

### 1.1 目标
通过多轮对话，把采购方自然语言转化为**完整、准确、可计算、可匹配、可解释**的结构化需求档案（`structured_demand`），并推动"档案→匹配→反馈"闭环。

### 1.2 设计原则
| # | 原则 | 落地 |
| --- | --- | --- |
| 1 | **Schema 驱动** | 抽取/追问仅在 Schema（分层+三态）坐标系内；自创字段只入 `extra_constraints` |
| 2 | **判定确定性优先** | 选项点击直写 / 枚举映射 / 数值比较走规则，LLM 只处理语义模糊部分（第 2/6 章） |
| 3 | **记忆分层** | 短期/工作/长期/领域四层不混用（第 4 章） |
| 4 | **可评估可回归** | 任何变更过评估集回归（第 7 章） |
| 5 | **成本可控** | Token 预算化；事实数据可离线分析（第 3 章） |

### 2.2 意图分类算法（route_intent）
```python
# 规则层常量（第 10 章：B/C 档确定性拦截，零 LLM 成本）
_REDIRECT_PAT = re.compile(
    r"哪家|谁(更好|合适|能|比)|更好|更合适|对比|比一下|比较|"
    r"推荐.{0,6}(厂商|厂家|家)|这家|那家|A厂|B厂|上面.{0,4}(厂|家)|"
    r"结果.{0,4}(好|准)|几个厂商", re.I)
_OFFTOPIC_PAT = re.compile(
    r"^(你好|您好|在吗|在不在|谢谢|再见|拜拜|嗨|哈喽|"
    r"你是(谁|什么)|今天天气|你会做|你能做|介绍一下你)", re.I)

def route_intent(message: str | None,
                 clicked_option: str | None,
                 state: AgentState) -> IntentType:
    if clicked_option:
        return IntentType.OPTION_CLICK          # 确定性
    if message is None:
        return IntentType.CONFIRM               # 无文本=确认动作
    m = message.strip()
    if re.match(r"^/done$", m, re.I) or "完成需求" in m or "就这样" in m:
        return IntentType.DONE
    if "确认" in m and state.current_slots.get("product_type"):
        return IntentType.CONFIRM
    if m in ("帮助", "help", "?") or m.startswith("/help"):
        return IntentType.HELP
    # ---- 第 10 章：B/C 档规则拦截（确定性；仅“采集中”会话 status=active 生效，10.1 红线3）----
    if _phase_active(state):                    # conv.status == "active"（由 StateStore 装载，2.1）
        if _REDIRECT_PAT.search(m):
            return IntentType.REDIRECT          # B档：厂商相关 → 重定向匹配详情（10.6）
        if _OFFTOPIC_PAT.match(m):
            return IntentType.OFF_TOPIC         # C档：无关话题 → 守门拉回（10.6）
    # A档（领域答疑）与填槽共用 FREE_TEXT 入口，由萃取 LLM 同一次调用判别（10.4）
    return IntentType.FREE_TEXT    # 补充/纠正/排除统一按文本解析，经 merge_slot 合并（6.4）
```

**节点语义与设计解释（为什么这样设计）**

**① 图结构的总设计逻辑（先看整体再拆节点）**

1. **单入口路由、确定性优先**：所有消息经 `route_intent` 一个入口分流，先用纯规则（选项点击 / 命令词 / 第 10 章 B/C 档）判出可确定意图，只有 `FREE_TEXT` 才进入 LLM——对应设计原则 2「判定确定性优先」，把"能用规则解决的"与"必须语义理解的"严格分层，控成本、控不确定、可单测；
2. **语义理解与状态变更解耦**：LLM 只产出结构化 `slot_delta`（或 `qa_answer`），状态变更统一经 `merge_slot`（确定性合并规则）落库——LLM 负责"看懂用户"，规则负责"决定怎么改"，防止模型破坏已确认槽位（6.4）；
3. **校验先于落库**：`validate_output` 在 `update_state` 之前，LLM 输出必须过 Schema 校验（Pydantic + 枚举）才允许进入状态，失败重试→降级，**保证脏数据不进状态、已确认档案不被污染**（6.3）；
4. **引导策略由规则掌控**：`decide_question` / `prompt_confirm` 均为确定性算法（按 Schema 顺序找未填项、关键维度齐才提示），LLM 只理解用户、不决定"问什么"——引导路径稳定、可复现、可评估（7.2）；
5. **确认即匹配的单端点收敛**：`confirm_submit` 一次性完成"生成快照（version++）+ 触发 match_runs"，无中间"待确认档案"步骤（M3 决策），保证"确认→匹配"原子衔接、状态不可分叉（8.1）；
6. **范围边界守门**：`redirect_to_results` / `guard_pull_back`（第 10 章）在入口用规则拦截 B/C 档，固定话术、零 LLM——红线是"厂商评价唯一权威 = 匹配结果"。

**③ 按流转图走读（节点做什么 + 如何流转）**

- **`start` → `route_intent`（入口）**：把用户消息/点击判为意图标签（2.2），按确定性优先顺序分流到四条路径之一；**每次对话只经这一个入口**。
- **主抽取路径（FREE_TEXT → respond）**——对话核心（需求打磨 + 领域答疑）：
  1. `extract_slots`：LLM 解析自由文本 → 产出 `slot_delta`（补充/纠正/排除）或 `qa_answer`（领域答疑，10.4）；
  2. `build_context`：把 Schema/画像/知识/历史/槽位/输出要求组装成 messages（3.1）；
  3. `rag_retrieve`：按当前需求检索领域知识注入（低于阈值不注入，5.2）；
  4. `llm_call`：统一调用 LLM（超时/重试/审计，0.4）；
  5. `validate_output`：Schema 校验输出；**失败且未达重试上限 → 回到 `llm_call` 重试**；仍失败 → 降级（6.3）；
  6. `update_state`：校验通过后统一落库（写历史 + `merge_slot` 合并 + 事实数据，3.5/6.4）；
  7. `decide_question`：按 Schema 选下一追问维度；**未完成 → 回到 `build_context` 开始下一轮**；全覆盖 → 进入 `prompt_confirm`；
  8. `prompt_confirm`：关键维度齐则提示"确认完成？还是继续补充？"（仅一次）；
  9. `respond`：把结果收敛为回复契约（text/options/updated_slots…）返回前端。
  > 注：A 档答疑轮（`qa_answer` 非空）跳过 `decide_question`，直接 `respond`（10.3）。
- **确定性路径（OPTION_CLICK）**：`write_slot_direct` 把选项值直写槽位（三态 SET）→ **跳过 LLM 抽取**，直接汇入 `build_context` → 走主抽取路径的 2~9 完成本轮追问；这是"判定确定性优先"的体现（零 LLM 成本）。
- **确认路径（DONE/CONFIRM）**：`confirm_submit` 生成需求快照（`buyer_requests` version++）+ 触发 `match_runs` → `SNAP` 落库（含物化统计）→ `respond` 返回跳转；会话置 closed（8.1）。
- **守门路径（B/C 档）**：`redirect_to_results`（厂商相关，B 档）返回固定话术指向匹配详情；`guard_pull_back`（无关话题，C 档）守门拉回；两者不调 LLM、不改槽位、直接 `respond`（10.6）。

### 2.4 状态转换表
| 当前状态 | 输入事件 | 动作 | 下一状态 |
| --- | --- | --- | --- |
| 采集中 | OPTION_CLICK | 直写槽位 | 采集中（若关键维度齐→可提示完成） |
| 采集中 | FREE_TEXT | LLM 解析 → merge_slot 合并（补充/纠正/排除；不新档案、不重匹配） | 采集中 |
| 采集中 | 领域答疑（A档，经 FREE_TEXT 判别） | qa_answer 简短回答 + 引导，跳过 decide_question（10.3/10.4） | 采集中 |
| 采集中 | REDIRECT（厂商相关，B档） | 重定向匹配详情话术，不回答优劣（10.6） | 采集中 |
| 采集中 | OFF_TOPIC（无关话题，C档） | 守门话术拉回主线（10.6） | 采集中 |
| 采集中 | DONE/CONFIRM | 确认并提交匹配：生成快照（version++）+ 触发匹配 | 已确认（closed） |
| 已确认 | 修改槽位 | 生成 vN+1 + 提示“是否重新匹配” | 已确认 |
| 已确认/closed | 开放问题 | 不再应答（状态锁定，10.1 红线3） | closed |
| 已确认 | — | 会话关闭 | closed |

```python
def decide_question(state) -> str | None:
    """从 Schema 未填项选下一追问维度；全部覆盖返回 None"""
    dims = load_schema_dimensions(state.current_slots.get("product_type"))
    for d in dims:                      # 按 Schema 顺序（关键维度优先）
        if d not in state.current_slots or state.current_slots[d].state in (WILDCARD,):
            return d
    return None

def should_prompt_confirm(state) -> bool:
    if state.completion_signal == CompletionSignal.USER_ACTIVE:
        return False                    # 用户已主动，不再提示
    anchor = state.current_slots.get("product_type")
    if not anchor or anchor.state != SlotTriState.SET:
        return False                    # 品类锚点未确认
    key = CONFIG["completion"]["key_dims"]
    covered = sum(1 for d in key if d in state.current_slots
                  and state.current_slots[d].state == SlotTriState.SET)
    if covered >= len(key) and state.completion_signal != CompletionSignal.AGENT_PROMPTED:
        return True                     # 关键维度齐 + 未提示过
    return False
```

### 3.4 历史裁剪/摘要算法
```python
def compress_history(history: list[TurnMessage]) -> list[TurnMessage]:
    """超过窗口则把更早历史压缩为一段摘要（演进：摘要缓存）"""
    n = CONFIG["history"]["window_turns"]
    if len(history) <= n:
        return history
    early = history[:-n]
    recent = history[-n:]
    digest = summarize(early)          # LLM 摘要：早期要点（一段）
    return [{"role": "assistant", "content": f"[早期对话摘要] {digest}"}] + recent
```

```python
def build_rag_query(state: AgentState) -> str:
```

### 6.4 槽位合并规则（merge_slot，需求打磨的变更落点）
用户输入（补充/纠正/排除）统一经 LLM 解析出 `slot_delta` 后，由 `merge_slot` 按**字段类型**决定合并语义——这是“需求打磨=对需求档案的完善与变更”的实现核心：

```python
def merge_slot(slots: dict[str, SlotValue],
               key: str, delta: SlotValue) -> None:
    """按字段类型决定覆盖/追加/排除"""
    field = schema_field(key)                 # 从 Schema 取字段类型
    if delta.state == SlotTriState.EXCLUDED:
        slots[key] = delta                    # 排除（负向过滤），直接覆盖
        return
    if field["multi"]:                        # 多选字段（os/interfaces/certifications）
        if delta.state == SlotTriState.WILDCARD:
            slots[key] = delta                # 明确"不限"
            return
        old = slots.get(key, {"value": [], "state": SlotTriState.SET})
        if delta.get("merge", "append") == "append":
            merged = old["value"] + [v for v in delta["value"] if v not in old["value"]]
        else:                                 # “覆盖”（如纠正成新值）
            merged = delta["value"]
        slots[key] = {"value": merged, "state": SlotTriState.SET}
    else:                                     # 单选字段（product_type 等）
        slots[key] = {"value": delta["value"], "state": SlotTriState.SET}
```

**规则要点**：
- **排除**（“不要 USB”）→ 直接置 `EXCLUDED`，参与负向过滤；
- **多选追加**（“再加个 CE”）→ 去重追加；
- **多选覆盖 / 单选**（“改成 Android”）→ 覆盖旧值；
- 未提及字段一律不动（`merge_slot` 只处理 delta 中的 key）；
- 任何变更**不生成新档案、不触发重匹配**——只有“已确认档案修改”才产生 vN+1（2.4 状态分界）。

### 7.2 稳定性（重点）
- **定义**：同需求档案 + 同数据集 + 同配置，多次运行结果一致或方差可控；
- **判定不稳定必须稳定**（槽位/verdict/完成判定），表述不稳定可容忍（措辞）；
- **采样流程**：同一输入重复运行 `N=5` 次 → 计算：

| 指标 | 建议阈值 |
| --- | --- |
| 槽位抽取一致率 | ≥ 95% |
| `match_score` 标准差 | ≤ 2 分 |
| Top-5 厂商集合重合率（Jaccard） | ≥ 90% |
| 排序位移（平均 |Δrank|） | ≤ 1 名 |

```python
def stability_metrics(runs: list[dict]) -> dict:
    return {
        "slot_consistency": mean(same_slot(runs)) >= CONFIG["eval"]["slot_consistency_threshold"],
        "score_std": std([r["match_score"] for r in runs]) <= CONFIG["eval"]["score_std_threshold"],
        "top5_jaccard": jaccard_over_runs(runs) >= CONFIG["eval"]["top5_jaccard_threshold"],
        "rank_shift": mean_abs_rank_shift(runs) <= CONFIG["eval"]["rank_shift_max"],
    }
```

**提升手段**（按优先级）：① 确定性优先（第 6 章）② 低温度（0.2）③ verdict 强枚举 Few-shot（架构 6.4.3）④ 相同输入缓存 ⑤ 回归纳入。

```mermaid
    PROFILE -.->|"新会话注入引导"| AGENT
```
- **画像只由需求侧行为驱动**（确认的 `structured_demand` + 对话显式偏好，异步提取）；**`match_results` 不进入画像**——① 语义错位（适配度 ≠ 长期偏好）② 数据隔离（厂商数据不混入买家画像，核心需求 3.4.2）③ 避免"结果→画像→引导→需求→结果"反馈环污染稳定性与评估纯净（7.2）；
- 两个**独立**闭环：`需求→匹配→评估→优化` 与 `需求→画像→引导`；
- **演进项**：用户对匹配结果的**后续行为**（点开/收藏/询价）可作画像弱信号（属用户行为，非匹配结果内容；PoC 不引入）。

## 9. PoC 落地项 vs 演进项 + 关键用例

### 9.1 PoC 落地 vs 演进
**PoC 落地**：状态图与类型（第 0/2 章）、上下文组装（3）、记忆四层（4）、RAG（5）、输出校验（6）、评估集 v1 + 六维脚本 + 稳定性基线（7）、事实数据（3.4）、**开放性问题处置（第 10 章：B/C 档规则拦截 + A 档并入萃取答疑）**。
**演进项**：历史自动摘要缓存、在线行为埋点与 AB、画像演化历史、主动澄清歧义、稳定性 CI 巡检、匹配结果行为弱信号（8.2）、**独立 QA 节点（若 7.2 回归显示萃取质量下降，10.6）**、**匹配结果对话化（厂商开放问答，10.6）**。

## 10. 开放性问题处置（领域答疑 / 守门 / 重定向）

> 定位：对话 Agent 的**范围边界设计**（产品决策：不做通用 chat，但需满足“用户问相关开放问题”）。
> 本系统是“需求萃取专用 Agent”，主线是 Schema 驱动的槽位萃取 → 确认 → 匹配；用户会话中必然出现
> **与需求决策相关的领域问题**、甚至**与厂商相关的开放问题**。本章定义**三档处置框架**、判定算法、
> 回复契约与事实数据埋点，作为第 2/3/6 章的行为扩展；
> 实现原则（与产品约定一致）：**尽量简单**——B/C 档用规则拦截（零 LLM 成本、确定性），
> A 档并入萃取调用（不增加调用次数）；**厂商评价唯一权威来源是匹配结果**，Agent 不做二次评价。

### 10.1 三档处置框架与设计红线

| 档位 | IntentType | 触发 | 典型输入 | 处置 | LLM 成本 |
| --- | --- | --- | --- | --- | --- |
| A 领域答疑 | `DOMAIN_QA` | 萃取层判别（10.2/10.4） | “机顶盒选什么OS？Linux和Android区别？” | 基于注入知识简短回答（≤3~5句）+ 引导回槽位；跳过 decide_question | 复用萃取 1 次 |
| B 厂商相关 | `REDIRECT` | 规则层（10.2） | “这两家谁更好？”“A厂能满足吗？” | 重定向匹配详情（参数判定/原文溯源），不回答优劣 | 0 |
| C 无关话题 | `OFF_TOPIC` | 规则层（10.2）+ 萃取层兜底（10.4） | “你好”“今天天气” | 守门话术拉回主线 | 0（规则命中）/ 复用萃取（兜底） |

**设计红线（不可破坏）**：
1. **厂商评价唯一权威来源 = 匹配结果**（`match_results`：`match_score` + 判定三组 `matched/partial/unmatched` + `source` 原文溯源）。对话 Agent **不生成任何厂商优劣评价**（B 档一律重定向），避免“聊天里说 A 好、匹配页说 B 好”的双标准，破坏可解释性与可信度（架构“纯净/透明”定位）；
2. **领域答疑只服务“需求决策”**：回答必须帮助用户把需求说准（A 档），不得演化为通用咨询；答完必须带引导回萃取（导向 `decide_question` 覆盖的槽位）；
3. **会话状态锁定**：仅“采集中”（会话 `status=active`）允许 A/B/C 处置；`confirm` 后会话 `closed`，不再应答开放问题（用户基于匹配结果交互）。

### 10.2 判定算法（route_intent 扩展，见 2.2）

两级判定，确定性优先（规则层零成本先判，LLM 只处理模糊部分）：

1. **规则层（B/C 档）**：`_REDIRECT_PAT`（厂商比较/推荐关键词）、`_OFFTOPIC_PAT`（闲聊/问候词）在 `route_intent` 内、会话 `status=active` 时命中即返回 `REDIRECT` / `OFF_TOPIC`；
2. **萃取层（A 档）**：领域答疑与填槽共用 `FREE_TEXT` 入口，由萃取 LLM **同一次调用**判别——用户问的是领域问题则输出 `qa_answer`（槽位不变），否则正常输出 `slot_delta`（10.4）；
3. **兜底**：规则未命中但实为 B/C 类的残余输入，由萃取层规则 8/9 兜底（10.4）。

> 取舍：不引入“独立意图判定 LLM 调用”——① 增加延迟与 Token（成本可控原则）② 多数 B/C 可由关键词确定性识别 ③ A 档并入萃取与“萃取即需求打磨”现状一致。

### 10.3 回复契约（AssistantOutput 扩展，见 6.1）

```python
class AssistantOutput(BaseModel):
    assistant_message: str
    options: list[str] = []
    updated_slots: dict[str, SlotValue] = {}
    completion_flagged: bool = False
    qa_answer: str | None = None   # 第10章：答疑/守门轮（A/C档）非空；填槽轮必须为 null
```

**装配规则（decide 分支）**：
- `qa_answer` 非空（答疑/守门轮）：`assistant_message = qa_answer`（含引导语），**跳过 `decide_question`**（不追问下一维度），`updated_slots` 必须为空/不变；
- `qa_answer` 为 null（正常填槽轮）：行为同现状（`decide_question` 产出下一追问）。

### 10.4 领域答疑与守门约束（A/C 档行为规则）

System Prompt「对话规则」补充（3.2 第 6 条后追加 7/8/9，见 3.2 全文）：

```markdown
7. 若用户询问与本轮需求决策相关的领域问题（OS 区别、认证要求、工艺/交期常识等）：
   基于“行业背景知识”简短回答（≤3~5句，可给倾向建议），末尾带一个引导回槽位的问题；
   知识库未覆盖则明说“暂不确定，建议咨询厂商确认”。本轮只填 qa_answer，updated_slots 为空。
8. 若用户询问厂商比较/推荐/评价（“这两家谁更好”等）：不回答优劣，回复
   “厂商对比请到匹配结果详情页查看参数判定与原文溯源”；若尚未生成匹配，回复
   “提交需求并完成匹配后，可在结果详情对比厂商”。
9. 若用户聊与需求无关的话题：礼貌拉回“我们专注于帮你梳理{品类}代工需求，继续吧”。本轮只填 qa_answer。
```

- **grounding 约束**：A 档回答必须基于第 4 区块注入知识（5.2）；知识不足时“明说不知道 + 引导”，不编造（延续规则 4）；
- **限长约束**：≤3~5 句（对应“避免长输出带走主线”）；不输出论文式长文；**（提示词层约束，模型自遵守；程序不截断回复——2026-08-14 修正，见 v2 §13.1）**
- **确定性强化**：B/C 档命中即走固定话术（模板常量，不调 LLM），保证措辞稳定、可回归（7.2）。

### 10.5 事实数据与可观测性

- `conversation_events.event_type` 扩展：`qa_answer`（A 档答疑）/ `redirect`（B 档重定向）/ `guard`（C 档守门）；payload 存用户原问 + 系统回复（限长）；
- `llm_call_logs`：A 档答疑仍记 `task=extract`（同一次调用），`output_raw` 含 `qa_answer`；B/C 档规则命中不产生 LLM 调用（无日志，符合“确定性优先”）；
- 评估（第 7 章）：`guidance_quality` 扩展统计**答疑后回到槽位的比例**（答疑轮之后一轮是否产出 `slot_delta`），纳入回归子集（7.3）。

### 10.6 边界与演进（PoC vs 演进）

| 能力 | PoC（P0，落地） | 演进（P2/KIV） |
| --- | --- | --- |
| B/C 档判定 | 关键词规则（10.2） | 意图判定模型 / 语义阈值 |
| A 档答疑 | 并入萃取调用（10.4，单次调用） | 独立 QA 节点 + 独立 Prompt（若 7.2 回归显示萃取质量下降则拆分） |
| 厂商开放问答 | ❌ 一律重定向（红线 1） | **匹配结果对话化**：对 `match_detail` 追问，回答仅引用该条判定 + `source` 原文（可溯源、不引入第二标准） |
| 知识供给 | 复用 `knowledge_items`（管理员维护） | 答疑命中统计 → 反哺知识库（管理员审核入库，M6 知识管理闭环） |
