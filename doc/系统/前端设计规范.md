## 1. 目标与技术栈

- **目标**：直接基于原型文档实现**真实可用的 PoC 前端**（非 Figma mock），并作为产品化迭代的基础。
- **技术栈**：
  - Vue 3 + Vite + TypeScript
  - Naive UI（基础组件库）+ 自研业务组件
  - Vue Router（路由）、Pinia（状态管理）
  - 可选：Tailwind 仅辅助布局，不强依赖
- **布局**：桌面端优先，内容区基准 **1440px**；后台侧边导航 **240px**。

## 2. 设计 Token（`src/styles/tokens.css`）

采用 **Primitive（原始值）+ Semantic（语义）两层**结构：所有组件只消费 **Semantic** token，不写死值；底层 Primitive 变更自动向上继承。同时通过 `<NConfigProvider :theme-overrides>` 将语义 Token 映射进 Naive UI 主题，使库组件自动跟随设计体系。

**命名约定**：Primitive 用 `--{类别}-{数值}`（如 `--blue-600`）；Semantic 用 `--{类别}-{语义}[-状态]`（如 `--color-primary-hover`）；组件只引用 Semantic 层。

### 2.3 接入 Naive UI

入口处用 `NConfigProvider` 将 Semantic token 映射进 Naive 主题，库组件自动跟随：

```ts
// themeOverrides
{
  common: {
    primaryColor: 'var(--color-primary)',
    primaryColorHover: 'var(--color-primary-hover)',
    successColor: 'var(--color-success)',
    warningColor: 'var(--color-warning)',
    errorColor: 'var(--color-error)',
    textColorBase: 'var(--color-text)',
    borderRadius: '8px',
    fontSize: '14px',
  },
}
```

- **P0 核心闭环**：02A 需求对话、02B 匹配结果、01C 能力录入、01D 能力档案、后台 03B/03C → 支撑「链路完整 / 需求萃取 / 匹配可解释 / 数据沉淀」

## 6. 目录结构（monorepo 双应用，一步到位）

前后端分离：前端 `frontend/`（pnpm workspace）+ 后端 `backend/`（独立 Python 工程）；根目录仅 `doc/`、`frontend/`、`backend/`、`README.md`。

```
xmsn-demo/
├── frontend/                     # 前端（pnpm workspace 根）
│   ├── apps/
│   │   ├── user-web/            # 用户端（公共+厂商+买家）
│   │   │   └── src/ (router / views/{public,vendor,buyer} / api / stores)
│   │   └── admin-web/           # 管理端（独立部署，内网/白名单）
│   │       └── src/ (router / views/admin / api / stores)
│   ├── packages/
│   │   ├── ui/                  # 共享组件库（COMP-001~040 实现）
│   │   ├── types/               # 共享类型（users/vendors/buyer_requests/match_results…）
│   │   ├── api/                 # 共享接口封装（vendor/buyer/admin）
│   │   └── tokens/              # tokens.css + Naive themeOverrides
│   ├── package.json             # workspaces
│   └── pnpm-workspace.yaml
├── backend/                      # 后端 FastAPI（独立 Python 工程）
│   ├── app/
│   └── requirements.txt
├── doc/                          # 文档（概念/需求/原型/前端规范）
└── README.md
```

> 特点：两个 app 独立构建/部署/发布，依赖各自收敛（admin 重依赖不拖累 user 首屏）；共享层经 `packages/*` 复用；前后端物理分离、独立演进；PoC 起即按此结构落地，避免后期迁移成本。

## 7. 关键交互约定

- **骨架屏**：AI 解析/匹配 3-5s 内先出占位（`NSkeleton`），超时按异常态处理（阶段6）。
- **匹配理由**：异步生成，详情展开显示“理由生成中…”；`source` 缺失或非法时不显示引用链接（阶段7.6）。
- **对话 Agent**：消息流式渲染（可选 SSE）；选项按钮组点击后自动填充输入框（可追加）；需求档案按**需求点实例**展示（已指定 + strictness 两档；当前需求 = 需求档案，label/options 由品类 Schema）（阶段7.2）。
- **状态徽标语义**：审核中=warning、已通过=success、已驳回=danger；关键参数不符=详情顶部红色警示条（阶段7.5）。
- **数据绑定**：厂商 `vendors`/`vendor_capabilities`；买家 `conversations`/`buyer_requests`/`match_results`；后台同 PRD 5.1。

## 8. 与后端接口约定（简）

- 按 PRD 数据实体定义 REST/JSON：`/api/vendor/*`、`/api/buyer/*`（chat/submit/match/history）、`/api/admin/*`（dashboard/requests/vendors，含审核/导出）。
- 匹配结果字段含 `match_score`（需求点等权，D10）/ `match_source` / 四组 `matched|partial|missing|unmatched_params` / `match_reason` / `risk_warning` / `ai_comment` / `source`（阶段7.7；`semantic_score` 仅召回、`param_hit_rate`/`critical_fail` 已移除）。
