### 一、产品定位与演示目标 
**一句话定义**：交付的是**真实可用的B2B代工制造供需智能语义匹配PoC**，让代工企业完整表达隐性制造能力，让采购方精准描述复杂需求，并由大模型实时完成语义匹配，返回满足需求的匹配结果。

> **概念界定**：本文及配套文档中的“Demo”不是传统意义的演示原型，而是**真实可用的概念验证产品（PoC）**——作为PoC，仅在范围与程度上取舍（如锁定消费电子代工垂直行业、控制厂商数量、简化非核心功能）：
>
> + **真实数据**：基于真实共创会员的公开数据，如实展示、不做脱敏与可见性控制
> + **真实运行**：按真实产品逻辑运行——真实注册、录入、审核、对话与匹配，无脚本化路径、无演示专用行为
> + **真实结果**：匹配结果与匹配理由均由系统真实计算产出，未经人工预设，所有对外展示即真实使用

**演示目标**：让投资人在3分钟内理解“语义匹配 vs 关键词搜索”的本质差异，并确信“纯净、去营销化”的供需连接是可行且高价值的。

**演示成功标准**（四维，均为可观察验收点，须在3分钟内达成）：

+ **链路实现完整**：真实账号现场走通「厂商录入/上传 → AI解析 → 审核 → 买家对话 → 匹配 → 详情 → 后台追溯」全链路，任一步骤返回真实结果、无阻塞
+ **需求萃取准确**：自然语言描述被准确萃取为结构化需求摘要（产品类型/OS/接口/二次开发等槽位正确），修正后即时更新——证明语义理解而非关键词命中
+ **匹配结果可解释**：结果含匹配度及其构成（语义/参数子分数）、✅/⚠️/❌分组与AI评语，且与需求语义相关；无排序权重，突出“产品力决定发现”
+ **关键数据沉淀**：演示中产生的需求与匹配记录即时落库、在管理员后台可追溯可见（与操作一一对应），存量100家档案完整可查

### 三、核心功能模块与页面结构 
#### 模块1：厂商端——能力提交与入库（供给端，AI自动生成档案） 
| 页面 | 交互细节 |
| --- | --- |
| **1.1 自助注册** | 手机号/邮箱注册，选择“我是厂商”，填写企业基本信息（含统一社会信用代码）+上传营业执照（jpg/png/pdf），作为真实性核验与审核依据 |
| **1.2 能力材料导入（仅文档）** | 拖拽/点击上传 PDF/PPT/Word（≤20MB），上传即自动解析；文档表格展示解析状态（解析中/已完成/失败，失败可重试）；**无表单、无自由文本**，能力 Schema 全部由 AI 从文档解析得出 |
| **1.3 能力档案生成（AI自动·只读）** | 提交原始材料后大模型自动提取结构化字段生成能力档案；无预览、不可人工编辑；材料变更自动重新生成，厂商可随时查看 |
| **1.4 审核状态** | 显示审核状态：预置厂商“已通过”，现场新注册厂商“审核中”，由管理员一键审核（通过/驳回） |


**数据说明**：Demo中预先导入真实共创会员的公开资料（业务信息与联系方式如实展示），确保匹配结果有真实参考价值。现场也可演示新厂商注册流程。

#### 模块2：买家端——需求描述与匹配（需求端） 
| 页面 | 交互细节 |
| --- | --- |
| **2.1 自助注册/登录** | 选择“我是采购方”，简化流程 |
| **2.2 需求对话Agent（核心）** | 聊天式UI，系统主动引导+用户自由输入：   • 开场：Agent自我介绍，询问需求类型   • 多轮引导：动态弹出选项（如“需要哪些操作系统？”→按钮组）   • 自由补充：用户可随时输入大段自然语言，完善/变更需求（如“不对，是Android”即纠正），仅更新对应槽位   • 萃取完成双通道：Agent判断（核心参数齐备后主动提示）或用户主动“完成需求描述”   • 需求Schema分层：固定（共通维度）+品类扩展+开放扩展；未指定参数默认全匹配，需求档案标注未指定项   • 需求档案：确认后生成摘要卡片；确认后修改生成新版本并提示是否重新匹配；提交匹配 |
| **2.3 匹配结果页（精简列表）** | 顶部“为您找到N家匹配的工厂”，列表项：   • 工厂名称、所在地、一句话摘要   • 匹配度百分比   • 点击展开详情 |
| **2.4 匹配详情（展开态）** | 顶部显示子分数副行（“语义相似度82% · 参数命中5/6”），下方按判定分三组：   • ✅ **匹配项**：绿色标签，列出一致参数   • ⚠️ **需协商/未声明**：黄色标签，如“交期30天 vs 45天（需协商）”“ISO13485（厂商未声明）”   • ❌ **不匹配项**：红色标签，关键参数不符时顶部出红色警示条   • **引用原文**：带出处的标签/评语可点击“查看原文”，打开原始文档定位高亮（提升可信度）   • **AI评语**：一段话总结匹配优劣（算法定义见《产品需求设计》阶段7） |
| **2.5 会话与需求匹配历史** | 多会话管理（新建/续聊/恢复）；每次“确认需求并触发匹配”生成需求匹配快照；历史可回看。会话记录完整对话过程，需求匹配必属某会话，可能含多条（对应BP“需求演化”） |


#### 模块3：匹配引擎
| 方面 | 说明 |
| --- | --- |
| **大模型** | 调用当前最强模型（GPT-4o、Claude、Gemini 或 DeepSeek），负责：①解析厂商自由文本/文档，提取结构化能力标签并生成一句话能力摘要（summary_text）②理解买家对话，提取结构化需求字段（需求萃取）并生成需求向量 ③计算供需匹配度（双通道打分）④生成匹配理由与可解释性文本，并附带出处引用（source，用于“查看原文”） |
| **入库流水线** | 厂商资料→文档解析→①结构化标签存入PostgreSQL（通道B参数匹配）②厂商级代表向量（1档案=1向量，通道A语义匹配）+原文切块向量（携带出处metadata，引用溯源）存入向量库 |
| **数据基础** | 真实共创会员资料预导入，PostgreSQL（结构化）+向量数据库（双轨：厂商级代表向量用于语义匹配 + 原文块向量用于引用溯源） |
| **匹配算法** | 双通道打分——语义相似度（向量，权重0.4）+参数命中率（LLM逐参数判定，权重0.6），综合匹配度=0.4·语义+0.6·参数命中；关键参数（产品类型/OS/认证）不符封顶50%并红色警示；过滤阈值30%；Demo阶段不训练专属模型，但效果要惊艳（完整算法定义见《产品需求设计》阶段7） |

| 页面 | 功能 |
| --- | --- |
| **4.1 数据概览** | 显示用户总数、需求总数、厂商总数、匹配次数 |

### 五、技术实现建议（PoC级别，更新） 
| 层面 | 建议方案 |
| --- | --- |
| **前端** | Vue + 聊天UI组件库，1~2周出高保真界面 |
| **后端** | Python FastAPI，对接大模型API，处理文件解析和向量存储 |
| **大模型** | 优先 DeepSeek，可选 Gemini 或 ChatGPT |
| **对话Agent编排** | 需求对话Agent采用**LangGraph**（显式状态机）实现：LLM推理 + 会话状态（`conversations`+需求槽位）+ 工具动作（确认摘要/更新槽位/触发匹配）；不采用传统LangChain；作为后续产品化的迭代基础，非一次性PoC |
| **数据存储** | PostgreSQL（结构化数据）+ 向量数据库（Pinecone/Milvus） |
| **文档解析** | Unstructured/LayoutParser提取PDF/PPT文本，再喂给大模型 |
| **会话与状态管理** | 会话持久化（PostgreSQL`conversations`表存完整对话过程）；前端维护对话上下文，后端用大模型维护结构化需求槽位，支持动态更新；每次确认匹配生成需求匹配快照（`buyer_requests`） |
| **部署** | 云端部署，确保投资人可远程访问体验 |
| **数据准备** | 提前收集100家真实共创会员资料，导入系统 |
